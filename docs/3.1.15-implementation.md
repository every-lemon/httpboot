# HTTP Boot 3.1.15 implementation status

The integrated source and opt-in packages use development version 3.1.15~dev6.
The legacy updater remains 3.1.14 until deployment qualification; development
artifacts must not be mistaken for a qualified automatic replacement.

## Implemented

- One HTTP Boot desktop app with Overview, Updates, Persistence, Diagnostics,
  Printers and Settings; Server policy, root-service enforcement, first-login
  folder selection, essential warnings, timestamped logs, copy/export, background
  updates and a separate explicit restart action. Update installation retains its
  completion state when the app closes or reopens.
- Root-only Server CLI and arrow-key setup, USB/SD creation and non-formatting
  updates with identity checks and remount verification, minimal localhost web console, Server
  and combined Server/Builder Debian packages. Server-only supports amd64/ARM64;
  Client and Builder are explicitly amd64.
- Versioned activation, account, policy, image and snapshot interfaces. Pairing
  uses a signed device CSR, six random characters, ten-minute expiry and approval
  rate limits. Authentication pins the approved public key and hardware binding.
- Assigned account records and stable IDs provisioned only into the Client RAM
  root. PAM obtains one persistent session, restores before login, and fences
  writes until restore completes. Explicit stale-session release invalidates old
  writes, including a commit already verifying content. Failed logout saves retain
  the RAM session.
- Public bootstrap-only server and authenticated streaming/resumable image
  downloads. Signed image manifests and exact-artifact boot proof gate publication.
  Shared native-HTTP/media startup handles activation, one bounded retry, previous
  verified images and offline recovery. A bounded verified kernel transition keeps
  an older bootstrap compatible with a newer desktop kernel.
- Independently built lightweight offline desktop, temporary account, network and
  repair tools, and a tabbed WebKit browser. Compressed recovery is limited to
  1,500,000,000 bytes. Atomic recovery-generation pointers retain previous verified
  caches when downloads or copies fail. Truly diskless Clients accurately report
  that offline recovery needs accessible cached storage.
- Home-only persistence with safe internal links and no symlink traversal, recursive change watches and
  two-second coalescing, unchanged-file identity caching, missing-content transfer,
  paged Server staging and atomic verified snapshot publication. Per-folder status
  is serialized; prior snapshots survive failed replacements. Database application
  saves require closure; live exports are never labeled verified backups.
- Approved per-user Flatpak installation references and verified app/runtime
  bundles, separate from private data and extra in-app downloads. App-only mode
  explains data reset. Encrypted pending-work export is limited to administrator-
  selected filesystem UUIDs and age recipients; RAM-only pending work remains clear.
- Bounded legacy saver pause/drain replaces maintenance stop/shutdown-save. It does
  not close user applications. CUPS/IPP/IPP-over-USB recipe and printer controls
  persist configuration without print documents. USB importer validates provenance,
  architecture and module compatibility and applies approved payloads at build time.
- Independent timezone-aware package/image schedules, daily 04:00 defaults,
  duplicate/conflict guards, matching Builder checks and qualified publication.
  Legacy migration preserves Asia/Taipei. Image/tool retention protects active,
  deployed, rollback and enrolled-card references and at least three successes;
  snapshot retention is separate. Package caches and build checkpoints are retained.
- Bounded redacted failure reporting and outage queues; non-destructive Sober
  diagnostics covering logs, processes, resources, permissions and graphics.
- Transactional isolated authority migration, same-key legacy certificate renewal,
  verified legacy-save import and private-image staging from an existing image.
  Original account/configuration/image/save sources remain intact for rollback.
- MIT source, explicit public package/source allowlists, example configuration,
  installation/migration instructions and third-party notices.

## Verification and rollout gates

See [verification results](3.1.15-verification.md) for completed tests and artifact
build results. The boot qualifier executes the production startup path in QEMU;
it never manufactures success from unit tests. The build and actual qualification
must pass before publication. A virtual boot does not qualify physical firmware,
SD/USB, drivers, printing, graphics or Sober.

The private Server now runs the development authority alongside its legacy service.
Three accounts, one enrolled Client and 18 selected saved folders have been imported;
original configuration, identities, images and snapshots remain intact. Existing
Client credentials authenticate on v2. The existing amd64 Builder has a separately
provided self-removing package installer; its installation is not yet confirmed.
Physical Clients have not been restarted or migrated. Keep the legacy service until
compatible Clients have booted and saved through v2, then close the deployment's
old anonymous image and NFS paths.
Fresh v2 exposes only bootstrap publicly. The actual restrictive private cutover,
physical tests and GitHub publication remain pending; publication also requires a
repository and authenticated access.

## Remaining integration work

Automatic v2 image scheduling currently executes on a combined amd64 Server/Builder.
A separate Builder uses the manual build, transfer and publication path; remote v2
job orchestration is not implemented. The private Server retains its legacy scheduling
during transition.

The USB importer validates and stages imports locally. Recovery-to-Server transfer
and approval are administrative steps, and the initial boot menu directs the user
to recovery tools rather than installing a driver in the initramfs. Automatic
Server upload and a complete in-bootstrap USB import flow remain to be implemented.
These limits are separate from the outstanding physical hardware tests.

The private pre-edit source backup is retained outside the public allowlist.
No user restart, application closure, snapshot deletion or live account migration
is performed by installing the development package. Follow INSTALL-v2.md for the
isolated rollout and preserve original images and verified saves.

## Development 10: Client login and desktop update

Account visibility is additive (`httpboot-server account-visibility NAME --no-visible`)
and independent of account IDs, passwords, assignments and app permissions. Hidden
accounts can still log in by entering their username. Server setup exposes this
policy under Login visibility.

The Client restores before pam_systemd starts the user session. A native PAM
conversation bridge reports restore progress; files transfer through at most four
workers and completed verified files can resume from RAM. HTTPS connections and
TLS contexts are reused with bounded pools. GNOME Terminal uses the bundled
DejaVu Sans Mono font and a versioned cell-spacing repair. HTTP Boot remains
available in Applications without opening automatically at login.

Software Properties, Additional Drivers, Software Updater and the old driver
launcher are removed from candidate images. Removal simulation refuses unexpected
dependencies; APT CLI, firmware and driver packages remain available.

Recovery uses an existing verified cache before downloading, reuses matching
content across release IDs, and checks integrity in the background. Offline
execution still checks signatures and hashes. Corrupt generations remain retained
while a replacement is verified and promoted. No arbitrary disk is formatted.

The Flatpak marketplace searches approved repositories (Flathub by default), shows
metadata and permissions, and authorizes persistence before installation. App and
runtime bundles receive an immediate verified save. App data is a separate choice;
uninstall preserves verified private data. Concurrent exports of one app serialize.

Client policy (`httpboot-server client-policy --file POLICY.json`) supports
`automatic_staging`, `safe_repairs`, `allowed_origins` and `preferred_origin`.
Origins are HTTPS Server addresses, not Client source-IP allowlists. Additional
TLS names retain the existing key and previous names. Image signatures trust the
enrolled deployment CA and serverAuth signer separately from transport hostnames;
mTLS and hostname verification remain required for network operations.

Automatic update staging never invokes a full user save or forces a restart.
Manual restart still requires successful saves. Staging retries are bounded;
worker failure restarts are limited to two starts per fifteen minutes. The
`safe_repairs` switch controls automatic staging retries. This does not implement
general-purpose remote repair commands or infer that a missed heartbeat is a freeze.

The first upgrade from rc9 still requires its existing Prepare update action.
Candidate source tests are not proof of graphical GDM behavior or performance on
physical hardware. Full image qualification and publication are recorded separately.

Runtime save repair (dev12): omit owned Unix-domain sockets from selected-folder
snapshots, and omit root Chromium/Electron SingletonSocket/SingletonLock/
SingletonCookie symlinks in the Chrome, ChatGPT and Codex profile rules. These
are process-local IPC/lock objects, not portable application data. Other external
links and unsupported special files remain rejected; previous verified snapshots
remain until a valid replacement commits. No app closure or forced restart.

Codex follow-up: normalize absolute links that stay within the selected folder
to relative links, then validate the complete virtual link graph as before.
Retain plugin version content and aliases, settings, authentication files and
session history. Exclude only `.codex/tmp/arg0` and `.codex/tmp/arg0-linux`
executable shim directories; retain other selected temporary-folder files.
Cross-folder links and chains escaping the selected root remain rejected.

### dev13: UI, boot-bound sessions, safe power and runtime DNS

HTTP Boot uses scrollable sidebar pages, a per-folder status table, visible
operation logs and asynchronous service requests. Restart/shutdown operations
verify all users' selected saves, then atomically release their Server leases
before requesting OS power actions. Database apps must be quit normally first.
The guard blocks shutdown while managed RAM sessions or boot-media updates remain
active; PAM logout and the network-ordered shutdown cleanup also release leases.
A denied power request reclaims only still-unclaimed sessions without restoring
over RAM work. Failed saves/releases never trigger automatic power-off.

Clients send boot-bound, authenticated session heartbeats every 30 seconds.
The Server retains a disconnected session for 900 seconds since last contact,
then rejects its old token and permits a new login. A new boot cannot extend
the previous boot's lease. Previous verified snapshots survive expiry; pending
work that exists only in disconnected Client RAM cannot be recovered by the
Server. Legacy Clients' authenticated current-boot desktop reports renew their
leases during rollout; Server restarts do not reset the expiry clock.

Every image must contain the runtime systemd-resolved stub symlink, never the
Builder's temporary resolv.conf. Installation finalizes the resolver and local
hostname mapping; qualification inspects the actual squashfs link before boot.
The boot qualification also performs logout, another login and a verified clean
power-off, and requires the test Server session to be released.

Power actions use logind's `PowerOffWithFlags`/`RebootWithFlags` interface with
`SD_LOGIND_ROOT_CHECK_INHIBITORS` (flag 1). This respects system shutdown locks
after the HTTP Boot guard releases its own lock. The old root `systemctl
--check-inhibitors=yes` invocation also rejected the requesting user's own login.
HTTP Boot enforces Server roles and multi-user authorization before requesting
power; it never uses force or skip-inhibitor flags. OS rejection details appear
in the app, and qualification reports a failed power operation immediately.

Qualification keeps a 40-minute total limit per VM and defaults to 180 seconds
per login/save/logout stage. Hosts with constrained RAM may explicitly set
`HTTPBOOT_QUALIFY_STAGE_SECONDS` from 180 through 600; the proof records that
budget. The same real login, restore, save, logout, power-off, and session-release
assertions remain required. Host RAM caps and file-backed memory are recorded
separately; constrained emulation is not a Client boot-speed benchmark.

### dev14: independent saves and matching application sign-in state

Each selected folder has its own two-second quiet timer and retry deadline.
An active application's file changes no longer postpone document saves, and
manual saves continue through other folders when one application is still open.
Shared-image process checks distinguish Chrome, the ChatGPT/Codex GUI profile
and the Codex backend; open descriptors inside protected profiles still block
a verified application save. No live inconsistent app profile is labelled clean.

A complete closed-app save atomically records a per-user mapping of verified
app snapshots and the selected keyring snapshot. Login restores that matching
set, while document folders use their latest saves. Interrupted app saves retain
the previous complete set. The last three sets protect their referenced snapshots
from ordinary snapshot retention. Existing installations without a complete set
remain readable through the legacy per-folder restore path. A policy capability
gates the new interface for older Servers. This preserves local credential files;
it cannot override an upstream authentication expiry or recover never-saved RAM.

The HTTP Boot overview provides Save selected data now and per-folder pending
reasons. A failed or unacknowledged power release keeps RAM intact; a denied
power request rejoins only an unclaimed lease, without restoring over live work.

Bootstrap Wi-Fi scanning captures failures outside the inherited error-trap
pipeline, retries at most three times, and keeps manual SSID entry available
after scan errors including status 141. Physical adapter validation is pending.
